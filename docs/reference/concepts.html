Architectural overview of the maf codebase. Read this before diving into any specific file.

1. The flow

A maf command runs in four phases:

  1. Macro expansion (load time) — maf-defcmd parses the declaration and generates a defun that wires the other three phases together.
  2. Resolve (call time) — given point and the calc stack state, produce a context alist describing what the command should operate on and how to commit the result.
  3. Body (call time) — the user's code. Receives clean values via bindings, computes a result, calls commit.
  4. Commit (call time) — applies the body's result to the calc buffer per the context's instructions.
maf-defcmd declaration                        (load time)
    │
    ▼
macro expansion → defun
    │
    ▼ (call time)
resolve → context alist ──┐
    │                     │
    ▼                     │
body (sees bindings)      │
    │                     │
    ▼  val                ▼
commit ─── reads context, applies val

Resolve and commit are peer concerns: resolve reads state into the context, commit writes state from the context. They share the context schema documented at the top of maf-resolve.el.

2. The target system

Resolve dispatches to one of six targets based on where point is and what calc state is active. In priority order:

Target When it fires Operates on
region An active Emacs region lies within one entry The run of chain terms (or the sub-formula) the region covers
selection An active calc selection exists anywhere on the stack The selected sub-formula
home Point is past the last stack entry (at or below .) The top stack entry
subexpr Point is inside an entry's formula text The sub-formula at cursor
equation Point is on a stack entry that is a relation (, !, …) LHS and RHS (body runs once per side)
entry Point is at line-prefix or EOL of a stack entry The whole formula

The cascade lives in maf--resolve-context. The predicates live in maf-lib.el (maf--at-*-p) and maf-sel.el (maf--sel-any-p); region is just use-region-p — the most deliberate gesture there is, so it outranks even an explicit calc selection.

Each target has a dedicated maf--resolve-target-X function that produces the target-specific portion of the context alist.

The equation target also fires by conversion: when home, entry, or subexpr resolves an :expr that is itself a relation, the context is rewritten to equation after the fact (see Relation mapping).

The region target frequently resolves as another target: whenever the region denotes something a plain subexpr could express, it collapses into a subexpr context and only the pointing gesture was new (see The region target).

2.1. Per-command targeting policy

Every conventional defcmd generates a NAME-targets variable — the narrowing gestures (region, selection, subexpr) the command currently honors — consulted on each run and passed to resolve as :narrowing, where it gates the cascade's three narrowing branches. The user retunes a command by editing the list; a gesture off it is treated as absent, skipped rather than consumed (commit reads :narrowing too, so a suppressed selection never pulls the pushed result into itself). The default value encodes the declared :scope, so shipped behavior is the variable's initial state.

The value is checked against the command's capability — :targets in the declaration, defaulting to all three, or to none for :scope entry commands — and a symbol outside it (including a typo) signals when the command runs. An empty capability generates no variable at all: bespoke-targeting commands (:targets custom, the entry-scoped workers) are simply not part of this surface. Workers name their variable after the public command with :targets-var (the two substitution workers share mafcmd-substitute-targets).

Across a flag dispatch the pressed key's policy governs, whichever variant answers: the invoking command sends its policy along raw, and the dispatcher validates it after consuming the I/H flags — a misconfigured variable must not strand a flag for the next command — then the variant prefers it (maf--dispatch-narrowing) over its own variable. I L maps by ln's variable though exp runs, H E by exp's though exp10 does, I | by vconcat's though vconcatrev does. A variant's own variable decides only its direct invocation.

2.2. Whole-entry scope

:scope entry in a command's options bypasses the cascade above: the sub-formula targets (region, selection, subexpr) never fire, and the command resolves entry at point — or home when point is past the last entry — however the pointing gesture looked. Point still chooses which entry; it just cannot narrow the subject inside it.

For commands with no sub-formula meaning: building a relation between two entries (mafcmd-equal-to), removing one (mafcmd-remove-equal), solving (mafcmd-auto-solve, mafcmd-solve-for), finding roots (mafcmd-poly-roots). Without it, the far more common gesture — point resting somewhere inside the formula — would resolve to whatever sub-formula happens to sit under the cursor and the command would act on that instead.

Commit honors the same intent: an entry-scoped push binds calc-use-selections to nil so calc does not redirect the new value into an active sub-formula selection, and the replacement entry carries no selection.

A caller can still put sub-formula targeting back on top of an entry-scoped worker, without resolve knowing anything about it: read point yourself before invoking the worker and pass what you found in a dynamic variable. mafcmd-isolate does exactly that — it hands maf--solve-target the sub-expression under point, which the worker solves the entry for — while mafcmd-auto-solve runs the same worker without looking at point at all. Two commands, one solver, and the targeting difference is the whole of what separates them.

2.3. Entry-scoped commit

:commit-scope entry is the other half of the same idea, and independent of :scope: where :scope decides what the body receives, :commit-scope decides where its value lands. With it, the value replaces the whole entry at the target's stack level instead of being spliced back into the sub-formula slot the target named. The cascade still runs in full — point narrows to a sub-formula, a region, a selection, as ever — and what changes is that the part it picked out stands as the entry afterwards, the formula around it discarded.

mafcmd-raise is the whole use: resolve a part, keep only it. Its body is one call, (commit expr), and every bit of the behavior is in where that value goes.

Such a push needs the calc-use-selections bypass above for the opposite reason an entry-scoped command does: its target may well be a selection, and letting calc redirect the push into that selection would splice the value back into the very formula the command exists to throw away.

3. The region target

Calc stores a sum as a left-nested binary tree and a product as a right-nested one — a + b + c is ((a + b) + c). A contiguous run of terms like b + c is therefore not a node, and calc's manual declares it unselectable ("there is no way to select the b - c + d portion"). The region target fills exactly that gap: an active region resolves to the run of chain terms it covers, and every defcmd works on it with no per-command code.

The region is never parsed as text. Its two endpoints map into the entry's flat rendering (core/maf-comp.el), and the innermost sub-formula containing both — the container — decides what the gesture means:

  • Not a chain (+=/-= or *) → resolve as subexpr on the container itself: the smallest sub-formula defined by two points, the same semantics as calc's j a.
  • A chain → snap the region outward to the run of terms it touches. Operator glyphs are connective tissue: a trailing + is absorbed, and a region covering only an operator pulls in both neighbors. Then:
    • run = the whole chain → subexpr on the container;
    • run = one term → subexpr on that term;
    • anything else → a synthesized region context.

Only the synthesized case is new machinery; note that a left-anchored sum run (a + b in a + b + c) or right-anchored product run is a real subtree and never reaches it.

3.1. Runs and signs

core/maf-chain.el views a chain as its rendered term list — each term paired with the operator glyph in front of it. Only the spine is flattened (left for sums, right for products, matching calc's reader); an off-spine sub-chain renders parenthesized, reads as a unit, and stays one term.

A run's :expr is the fold of its covered terms, each keeping its chain sign, so the fold is exactly the value the run contributes to the chain. Selecting 4 x - 12 in a - 4 x - 12 yields -(4 x) - 12 — including the leading term's sign, whose glyph sits just outside the region — and that is what keeps the splice value-preserving: the sign is structural, not textual.

3.2. Region commit

A synthesized run has no cons to eq-splice, but its container does: commit rebuilds the chain — the untouched terms keep their original conses, so their text re-renders identically — with the body's result joining as one + (or *) term, then splices the rebuilt chain at :chain-ref through the ordinary eq-based path. A result that is itself a same-kind chain is absorbed as terms rather than spliced as a parenthesized unit (commuting a b in a b c gives b a c, not (b a) c); the absorption only reassociates.

Resolving consumes the gesture — the mark deactivates — while a resolve error leaves the region active for adjustment. Version-1 scope is +=/-= and * chains; / is excluded because its textual and structural readings diverge (b / c inside a / b / c contributes 1/(b c), not b/c).

4. The context alist

Everything resolve learns is carried in one flat alist — the context — which the later phases read but never mutate. maf--resolve-context assembles it from three layers, appended in order, so earlier keys shadow later ones:

  1. Target keys — from the matched maf--resolve-target-X function, possibly converted by relation mapping (below).
  2. Declaration options — the defcmd's OPTS merged in verbatim. Known keys are :arity (the symbol unary or binary), :prefix (the trail label string), :map (-1 opts out of relation mapping), :pair (-1 keeps a relation argument whole at an equation target), :commit-scope (entry lands the value as the whole entry — see Entry-scoped commit), and the I/H variant links (command symbols); any other keyword passes through untouched, so resolve/commit extensions can define their own.
  3. Ambient state — snapshots taken at resolve time: :keep (the calc-keep-args-flag boolean) and :point (an alist of point's placement, captured before the rewrite destroys it — see Point restoration for its keys).

For example, a binary mult command (:prefix "mult") invoked with point on the x of 2: 6 x + 12, with 5 at the top of the stack, resolves to: 

((:target    . subexpr)                ; target keys
 (:expr      . (var x var-x))
 (:expr-ref  . (var x var-x))          ; the encased cons from the entry
 (:arg       . 5)
 (:m         . 2)
 (:commit-m  . 2)
 (:commit-n  . 1)
 (:post-pop  . 1)
 (:reselect  . nil)
 (:arity     . binary)                 ; declaration options
 (:prefix    . "mult")
 (:keep      . nil)                    ; ambient state
 (:point     . ((:pos . 7) (:line . 1) (:affinity . nil))))

Two consumers read it. The macro-generated command wires the body:

  • :target — a symbol: region, home, selection, subexpr, equation, or entry. Selects the execution shape (single body run vs once per side); commit also dispatches on it to pick the splice path. The macro also binds it to the dynamic variable maf-target around the body, for bodies whose result shape depends on where it lands (see Multi-value commit); most bodies ignore it and just act on EXPR.
  • :expr — the clean operand, a normalized calc formula, bound as the body's EXPR.
  • :arg — the second operand for binary commands, a normalized calc formula, bound as ARG; nil for unary.
  • :rel-op, :lhs, :rhs — equation target only. :rel-op is the relation's head symbol (calcFunc-eq, calcFunc-neq, calcFunc-lt, calcFunc-leq, calcFunc-gt, or calcFunc-geq); :lhs and :rhs are the two sides as normalized formulas. The body runs once with EXPR bound to :lhs, once to :rhs, and the two results are reassembled under :rel-op before a single commit.

maf--commit applies the result:

  • :commit-m, :commit-n, :post-pop — integers encoding the push/pop recipe: the stack level to push at, the entries popped there first, and the entries popped from the top afterward (see The commit recipe).
  • :m — integer stack level (1 = top) of the target entry; where commit fetches the full formula for splicing.
  • :expr-ref — the encased cons cell for the eq-based splice. Selection and subexpr only (see Encasing).
  • :chain-ref, :chain-kind, :pre-terms, :post-terms — region target only: the chain cons commit splices the rebuilt chain at, its kind (sum or prod), and the untouched terms on each side of the run (see The region target).
  • :reselect — boolean: whether the committed result becomes the new selection.
  • :prefix — string: trail label recorded with the operation.

The commit instructions are computed at resolve time, not by commit: each target function knows how its own result should land (including the keep-args variants), and commit just executes the recipe. That split is what keeps commit target-agnostic apart from the splicing special case.

The authoritative key-by-key schema lives at the top of maf-resolve.el.

4.1. Point restoration

Calc's command epilogue parks point at home after every command. The :point snapshot is what undoes that: it is consumed after commit, as the generated command's last act — restore has to run once calc-wrapper returns, because anything done inside the wrapper is clobbered by the epilogue.

The snapshot (maf--point-snapshot) is itself an alist of three keys:

  • :pos — integer: point's buffer position.
  • :line — integer: the line number at point.
  • :affinity — a symbol classifying the position semantically: home when point was at or below the . line, eol at end of line, bol in the line-number prefix, or nil inside an entry's formula text.

maf--point-restore applies it:

  • home affinity restores nothing; calc's default placement already matches.
  • Otherwise point returns to :pos, corrected back to :line if the rewrite shifted it, and eol=/=bol affinity is re-applied on the line rather than the exact position.

Line-based restore is correct for every target because of a commit invariant: commits only pop entries at the target's level and below it in the buffer (:post-pop consumes the stack top, which is displayed below the target), so the target entry's line never moves.

One case restores by anchor rather than position: point on a glyph the resolved sub-formula renders itself — its operator, a comma, its function name. Resolve records the glyph's index as :point-anchor, commit returns where the committed node landed (its cons and stack level), and point goes to that node's same structural glyph, wherever the rewrite moved it. Commuting sin(y) = k from the = leaves point on the = of k = sin(y), and the anchor survives the glyph itself changing (commuting x < y parks point on the >). It also holds through relation mapping — factoring from the = re-anchors on the rebuilt relation's = — and spaces count as glyphs, since a juxtaposed product renders its multiplication as nothing but a space: commuting 2 (4 + 3 x) from that space lands after the ) of (4 + 3 x) 2. Atoms have no anchor, and anything the anchor can't locate afterwards \(non-flat renderings, a consumed entry) falls back to the positional restore. The node-to-text coordinate machinery lives in core/maf-comp.el. Sticking point to the same atom when the formula reshapes around it is deliberately deferred.

4.2. Relation mapping

A relation can become the subject without point sitting on a relation entry: the top entry at home, an entry target at the margin, or the relation node itself under point as a subexpr. maf--resolve-map-relation inspects every home, entry, and subexpr context after resolution; when its :expr is a relation, it prepends the equation keys — :target, :rel-op, :lhs, :rhs — onto the context. The base target's commit fields remain (only :target is shadowed), so the rebuilt relation replaces exactly what the base target would have replaced.

Commands whose body consumes or produces relations whole (solve, mapeq, the relation builders) opt out with :map -1, which also disables the direct equation branch of the cascade. So do the concatenators (the | family), for a different reason: they take a relation as one element of the vector they build, so two stacked equations give [x = 1, y = 2] — calc's own spelling of a system — where mapping would pair them into the single equation [x, y] = [1, 2]. At a mapped equation target, a relation argument ordinarily pairs its two sides with the subject's sides — and signals unless both relations are . =:pair -1 keeps that argument whole without disabling per-side mapping of the subject, and the pairing check goes with it: mafcmd-let's assignment x = 2 binds across a < subject as readily as an = one.

Synthesized region contexts are exempt by construction — a run of chain terms is never a relation. Degenerate regions resolve as subexpr, though, so a region snapped to a whole relation node maps per side like any subexpr would.

4.3. The map flag

mafcmd-map-flag (M) sets maf-map-flag through calc's fancy-prefix machinery, so it chains with K=/=I=/=H and expires like them (maf--map-flag-expire sweeps it after a command that does not read it; keystrokes in a minibuffer never spend it, so it survives a prompting command's own prompt through to the defcmd worker). The next defcmd consumes the flag at resolve time: a relation subject takes the equation target even past :map -1 — the flag is the explicit request to map, so M | on two stacked equations does pair them into [a, c] = [b, d], and a selected relation, ordinarily held whole as a deliberate gesture, converts too, though a forced :map -1 command splits only an = (maf--resolve-mapflag-relation-check: an ordered relation or != refuses, since a command cannot say which way it bends the direction, and I already means the inverse variant) — and a vector subject runs the body once per element (maf--defcmd-map-vec; nested vectors recurse, the arg of a binary command shared across the runs). Any other subject refuses. Where M M maps a formula you type and M $ one from the stack (maf--map-flag-keys, live for the keypress after M), M maps a command, with no operator table behind it the way calc's V M has.

5. Encasing

Calc's mechanism for distinguishing duplicate atoms by eq.

Consider 1 + 1 = (+ 1 1) in calc. The two 1=s are the same integer object — both =eq and equal. If the user selects "the first one", you can't tell them apart structurally.

calc-encase-atoms (in calc's calc-sel.el) walks the formula and replaces each naked atom with (cplx atom 0) — a fresh cons cell each time: 

(+ 1 1)    →    (+ (cplx 1 0) (cplx 1 0))
                ;; ^^^^^^^^^^  ^^^^^^^^^^
                ;; cons #A     cons #B   ← now distinguishable by eq

Calc displays (cplx N 0) as just N (complex with zero imag), so the user sees nothing different.

calc-prepare-selection calls this on a stack entry and mutates the entry in place via setcar. So once selection-related machinery runs on an entry, that entry's atoms are encased until something normalizes.

This matters for us in two places:

  1. The body shouldn't see encased values. Most calcFunc-* functions dispatch on type, and (cplx ...) inputs route to complex-number branches that produce floats. (E.g., calcFunc-sqrt on (cplx 16 0) gives a float instead of the integer 4.) So resolve exposes a clean :expr via math-normalize.
  2. Commit's splice is eq-based. calc-replace-sub-formula matches by eq, and only the original encased cons matches the cell in the entry's formula. So resolve also exposes :expr-ref — the actual cons cell — for commit to use.

6. :expr vs :expr-ref

The body and commit operate on the same sub-formula but at different points in the data flow:

  • :expr — clean form, for the body to compute with
  • :expr-ref — encased cons, for commit's eq-based splice

They're only different for selection and subexpr (the targets that splice into a parent formula). home and entry don't have :expr-ref — they operate on whole entries, no sub-formula targeting needed.

A synthesized region run has an :expr but no :expr-ref at all: the run is not a cons in the entry, so there is nothing to eq-match. Commit instead rebuilds the containing chain and splices it at :chain-ref — which is a real node — through the same eq-based path.

7. Reselect

When commit pushes the new entry, should the result be re-selected?

  • selection target: yes (:reselect t). User explicitly set a selection; preserve their intent by re-selecting the new sub-formula.
  • subexpr target: no (:reselect nil). User just had a cursor position; no explicit selection to preserve.
  • region target: no (:reselect nil). The gesture is transient — the mark deactivates at resolve — and there is no prior calc selection to preserve.
  • home / entry / equation: not applicable (no sub-formula selection).

Commit reads :reselect and passes val-encased (or nil) as the SELS arg to calc-pop-push-record-list.

8. Keep-args

calc-keep-args-flag is calc's mode where operations don't consume their inputs — the result is pushed above them rather than replacing them.

Resolve snapshots the flag as :keep and derives commit instructions accordingly:

Target Normal mode Keep-args mode
home Pop arity entries, push result at top Push result at top, no pop
selection Replace selected entry in place Push result on top, leave entry
subexpr Replace entry in place (sub-formula spliced) Push spliced result on top
region Replace entry in place (chain rebuilt) Push rebuilt result on top
entry Replace entry in place Push result on top

In schema terms, :commit-m, :commit-n, and :post-pop encode the recipe; commit just executes it.

A hand-written command may read :keep for something else. maf-dup (RET) does: a duplicate consumes nothing to begin with, so the flag cannot change what lands on the stack, and it spends it on point instead — K RET duplicates and holds point where it was, exactly as C-u RET does. RET only sees the flag at all through maf--fancy-prefix-keep; calc's fancy-prefix dispatch clears its flags before any control character, and before any function key too.

That guard reads the maf-command property. maf-defcmd stamps it on every command it defines, since their commit path reads :keep; a hand-written command that wants the same treatment sets it itself, as maf-dup-or-clear-selections does. A key with no marked command behind it keeps calc's own behavior, which matters because the flag is not inert — maf-dup branches on it.

9. The commit recipe

Three context keys describe what commit should do:

  • :commit-m — stack level to push at (the M arg to calc-pop-push-record-list).
  • :commit-n — entries to pop at :commit-m before pushing (the N arg). This is the "replace in place" knob — 1 means "pop the old, push the new", 0 means "insert on top of it."
  • :post-pop — entries to pop from the top after the push. This consumes the binary arg in non-keep mode.

Visualization for binary selection at :m = 2 (non-keep): 

Before:                              commit-m=2, commit-n=1, post-pop=1
1: arg                ──┐
2: selected entry  ──┐  │
                     │  │
                     ▼  ▼
After push at m=2 (pop 1 at level 2, push new):
1: arg
2: new (with spliced sub-formula)
                     │
                     ▼
After post-pop 1 from top:
1: new

Two operations, one push and one optional post-pop. See maf--commit-push.

10. Multi-value commit

A body normally commits one expression. At a whole-entry target (home, entry) it may instead commit a list of values, which lands as one stack entry per value: calc-pop-push-record-list already distinguishes the two, reading its VALS as a list of values when the car is an integer or a cons, and as a single value otherwise. A calc formula always leads with a symbol head (+, calcFunc-sin, vec), so the two never collide.

A slot target (selection, subexpr, region) cannot take a list: its result is spliced into one cons in a larger formula, so exactly one expression fits. Committing a list there signals.

Bodies that can produce either read maf-target to tell which applies: 

(cond ((eq maf-target 'equation)                ; forced per-side run
       (if (cdr parts) expr (car parts)))       ; a side's slot fits one
      (t parts))                                ; one entry per part

mafcmd-unpack is the case in point — [x, y] becomes two entries. Entry-scoped as it is, the only slot it can meet is a relation's side when the map flag forces a per-side run, and that slot fits a single part.

11. Widening the sub-formula target

A slot fits one expression, so a command whose result does not fit the node under point would simply do nothing there — the key would look broken from most positions in a formula. :widen is the way out: the declaration names a predicate, and resolve walks from the node under point outward through its ancestors, stopping at the innermost one the predicate accepts. That node becomes :expr and :expr-ref. Nothing accepted out to the whole entry means the node under point stands, and the command no-ops as before.

The walk starts at the node under point, so a position that already had an acceptable target is unaffected — widening only ever fills in where the command used to be silent.

For mafcmd-flatten the predicate is "a vector with nesting to remove", so the command means flatten the innermost nested vector around point: 

[[1|, 2], [3, 4]]      =>  [1, 2, 3, 4]      ; point names the flat row
                                             ; [1, 2]; the matrix holding
                                             ; it has the nesting
x + [[1, 2], [3, 4]]|  =>  x + [1, 2, 3, 4]  ; already acceptable: no walk
x + [1, 2]|            =>  unchanged         ; nothing nested out to the
                                             ; entry

Explicit calc selections are never widened — an active selection is a deliberate gesture, and the selection target does not route through maf--resolve-widen.

The user reaches the same walk by hand: maf-up-expression (C-M-u) moves point out to the enclosing sub-formula over the same ancestors (maf--resolve-ancestors), so where :widen fixes one command's reach from a declaration, the motion re-aims every command by putting point where it names the parent. It lands only where resolve agrees — an ancestor the rendering gives point no way to name, such as a matrix row, is walked past rather than landed on — and it carries an active selection along with it, that being what a command would resolve to instead of point.

maf-forward-operand (M-e) walks the same landings sideways rather than upward: every operation of the entry is one stop, the whole entry among them, each at the first glyph it renders itself, so a few presses offer every compound target of the entry in turn. A glyph is the node's own when the node renders it wherever it stands — its operator, its function name, a vector's brackets — which the parens calc prints only where precedence demands them are not: they belong to the context that asked for them, so the sum in 3 (x - 5) is named at its -, as it is at the top of an entry. Landing on the ( instead put it one column past the juxtaposition space naming the product around it, and the walk stopped there with the rest of the entry ahead of it. Both the climb and the walk pass the pair over (maf--comp-own-brackets-p), so the stops are the operator glyphs in display order, an inner operand coming before an outer one whose operator is printed to its right. The nouns are left out — a number or a variable is maf-forward-noun's (M-f) to walk — so the two motions divide the entry between them rather than covering the same columns, and an entry that is a bare atom offers no stop of its own. Where the climb asks resolve one ancestor at a time, the motion asks it at every column of the entry and keeps one landing per node (maf--operand-positions), so both read the rendering back through the resolver rather than computing a column and trusting it. That is what lets the walk work in every rendering. The composition carries the formula's shape either way, but what a walk of it yields is a flat character count, and that is an address only when the entry is drawn as one row of glyphs: Big language draws a quotient as three lines, a raised exponent above its base, a matrix as one line per row. Asking costs a resolve per column and pays for itself — the stops come back in the order the rendering draws them, down the lines as well as across, and a node the rendering gives point no way to name (a matrix row, whose brackets calc tags to the matrix itself) is simply no stop, having nowhere to be named at. The walk is confined to the entry point sits in: the first and last stops are where it stops asking, and it signals at the margin rather than carrying point into a neighbouring entry, which is a line of its own to move to. maf-backward-operand (M-a) is the same walk the other way, over the same stops, so the two retrace each other.

maf-goto-left-side (() and maf-goto-right-side ()) arrive at one particular landing in one press: the whole of a relation's left or right side, the largest formula there is on it, where the climb would reach it a level at a time. The relation is the innermost one point sits in, so a term inside one element of [h = 0, p = -4, k = 0] crosses within its own equation rather than finding the vector around it, and the entry's margins — the line-number prefix, the end of the line — cross the entry's own relation. Like the climb it asks the rendering where the side is nameable rather than computing a column (maf--up-node-position), so it works in Big language too, and it carries an active selection along for the same reason. Pressed from the side it already names, either key crosses to the other one instead of standing still — the side is as far out as that end of the relation goes — so one key walks the relation, and the cycle turns on where point stands rather than on which key put it there. Home is the one place the keys mean something else: there is no entry at point to move within, and they keep the blank-vector gesture the edit module gives them (maf-edit-add-vector).

11.1. Widening a rewrite marker

maf-distribute (j D) and maf-merge (j M) widen along the same ancestors, but for a different reason, and so outside the :widen declaration. They are not defcmds: calc's DistribRules and MergeRules are written against a marked sub-formula, and every rule in them matches the formula around the marker rather than the marker itself — 

x * select(a + b)   :=  x*select(a) + x*b

— so the rewrite needs the whole entry with the target marked inside it, not an isolated sub-expression spliced back into a slot. The node point names is therefore usually one level too deep to be the marker: on the a of x (a + b), the rule that fires is the one reading the product, whose marked part is the sum.

A marker is therefore always a part of the formula being rewritten, never that formula itself, and the node under point can miss in either direction: it may be too deep to be the marker (the a above), or it may already be the formula to rewrite, with the marker one level in — point on the ln of ln(x^2).

So maf--sel-rewrite-widen walks rewrite sites, from the node under point out through its ancestors, trying each site's own parts as the marker. The node under point is itself the first site, which is what lets point stand on a function name or an operator; it comes up again as a candidate marker when the walk reaches its parent, so standing on a term still marks that term. Innermost site wins, and within a site the part point is in. The upshot is that every column of an entry reaches the same rewrite: 

ln|(x^2)  ln(x|^2)  ln(x^2|)   =>  2 ln(x)      ; all of them
x|*(a+b)  x*|(a+b)  x*(a|+b)   =>  x b + x a    ; all of them

Where :widen takes the innermost ancestor a declared predicate accepts, this takes the innermost site at which some rule matches. The test is the rewrite itself rather than a predicate, since "does a rule reach this" is not a property of the node alone. Nothing matching out to the whole entry means the entry is left untouched.

At home, where point names no part, the same walk runs over the whole entry outermost-first (maf--sel-rewrite-entry). Calc's own reading of an unmarked entry — let select( ) match wherever it can — is not usable, for two reasons that pull in opposite directions:

  • It matches too much. The sign rules below match every expression there is, so a bare sqrt(x) rewrites to sqrt(-1) sqrt(-x), with no marker relationship to test and so nothing for the sign guard to catch.
  • It reaches too little. The rewriter normalizes its input, which can fold away the very thing a rule was about to match: x^a x^b becomes x^(a + b) before MergeRules ever sees it, and j M at home did nothing on an entry it plainly should merge.

Walking marked candidates fixes both, and puts home on the same footing as every other position — one code path, sign guard included.

One family of rules has to be held off for the walk to get anywhere. Two DistribRules mark a bare negation (select(- a) ^ x, sqrt(select(- a))), and calc's matcher reads any expression as -a, binding a to its negation — -(-a) is a. So they match every marker there is, and sitting early in the set they claim the first level the walk tries, before the rule the gesture meant: 

ln(x|^2)   =>  ln((-1)^2 (-x)^2)   ; the sign rule, equal and useless
ln(x|^2)   =>  2 ln(x)             ; the log-of-a-power rule, one out

Both rules carry the marker from n to -n, so maf--sel-sign-peel-p counts a result marking exactly math-neg of what went in as no rule having fired, and the walk carries on outward. The test is the sign of the marked node itself, not the marker relationship, so a genuinely negative operand still splits (sqrt(-x) > =sqrt(-1) sqrt(x)). Both nodes compared are read back out of whole expressions the rewriter saw, never off the stack entry — an entry's atoms are encased (see Encasing), and (cplx 4 0) would never match a plain 4.

The same rule holds as above: an active selection is never widened, so j D on a hand-made selection is faithful to calc-sel-distribute, which marks exactly what was selected. It is also what picks the entry, ahead of point, as in maf--resolve-context: a selection standing on a lower entry is the subject even when point has wandered to another.

11.1.1. Scoping the rewrite to the site

Only the site is handed to the rewriter, and the rest of the entry is carried over untouched. Calc's calc-rewrite-selection normalizes the whole entry on the way in, which reaches sites the gesture never named — merging the logarithms of ln(a) + ln(b) + x^p x^q also collapses the powers, two structural changes for one keystroke. maf's other commands leave what they did not target alone, and these follow them rather than upstream. Scoping costs no matches: the site is where the rule matches, being the formula around the marker.

The same reasoning applies after the rewrite. There is no normalizing pass over the finished result and no calc-encase-atoms (see Encasing) — the rewriter already normalized the site, and re-running either over the whole entry would undo the scoping. The coefficient ordering is likewise confined to products carrying the marker, so distributing the logarithm in ln(x^2) + y 3 does not also reorder the y 3 the user wrote.

11.1.2. Ordering without folding

A distribution has to commit unsimplified, or calc's simplifier undoes it — x^b x^a folds straight back to x^(b + a). But calc's canonical ordering lives in that same pass, so suppressing it also loses the convention that a coefficient is written first, and ln(x^2) would commit as ln(x) 2.

The ordering cannot simply be run afterwards. Both ways of asking calc for it were measured against the raw result, and both undo the work:

approach ln(x^2) x^(a + b) sqrt(3:4)
raw, simplifier off ln(x) 2 x^b x^a sqrt(1/4) sqrt(3)
normalize under ambient 2 ln(x) x^(b + a) 1.73205 sqrt(0.25)
ambient, marker still in 2 ln(x) x^(b + a) 1.73205 sqrt(0.25)

The marker does not protect here the way it does in a merge: there it sits directly on an operand of the sum being folded (x*(3 + select(2))), while in x^select(b) * x^a it is buried in an exponent and the outer product folds around it.

11.1.3. Correcting calc's power-merge rules

Four MergeRules gather powers of unlike bases wrongly, and each loses the value rather than merely spelling it oddly. Stock calc-sel-merge gives the same answers — none of it is maf's doing.

Two divide by the wrong base, reading the numerator's base as b where every sibling reads a: 

(a^x) / select(b^x)  :=  select((b / b) ^ x)     ; b/b = 1
(a^x) / select(b^y)  :=  select((b / b^(y-x)) ^ x)

Two more get the exponent arithmetic wrong. Gathering a^x and b^y under a single power of x needs (b^(y/x))^x = b^y, but the rules subtract where they must divide, yielding b^(x(y-x)): 

 (a^x) * select(b^y)  :=  select((a * b^(y-x)) ^ x)
select(a^x) / (b^y)   :=  select((a / b^(y-x)) ^ x)

At a=2, b=4, x=4, y=2 the entry a^x / b^y is 1 and calc answers

maf corrects all four rather than mirror a wrong answer, the same call it makes for the fraction the negation rule mangles. The corrections are swapped into whatever var-MergeRules currently holds, matched by left-hand side and memoized (maf--merge-rules), rather than kept as a second copy of the set — the pattern maf--jump-rules already uses, and for the same reason: a hand-kept copy drifts the moment calc edits the set upstream, whereas an unmatched left-hand side simply replaces nothing.

So maf--sel-coefficient-first applies the one part of the ordering that provably cannot undo a rewrite: moving numbers to the front of a product. Numbers commute with every operand there is, matrices included, so it is a reordering and never a change of value, and it folds nothing. A symbolic coefficient is left where the rule put it (log(x^p, b) > =log(x, b) p); matching calc there would mean reproducing an order that is not a simple total order over expressions, calc's own product ordering being decided inside math-mul and its simplification rules rather than by math-beforep.

12. Binary on selection-like targets

Selection, subexpr, entry: each can support binary commands, but the "second operand" needs to come from somewhere. Convention: the top stack entry serves as :arg.

This creates a self-reference problem when the target itself is the top:

  • selection / subexpr / region — reject. If the selected sub-formula is in the top entry, the arg would be the entry containing the sub-formula. No coherent commit semantic. Resolve errors out.
  • entry — ergonomic shift. If point is at the line-margin of the top entry and arity is binary, :m is shifted from 1 to 2. The top becomes the arg, the entry below becomes the target. User doesn't have to position point on the operand whose value will change.

Choice reflects the difference between "I pointed at this exact sub-formula" (selection/subexpr — error keeps the user honest) and "I'm near this entry" (entry — shift is friendlier).

13. Inverse / Hyperbolic variants

Calc's I and H prefix flags reroute a defcmd to a declared variant command (the :inverse, :hyperbolic, and :inverse-hyperbolic options — e.g. I on mafcmd-ln runs mafcmd-exp). Dispatch happens before any context is resolved, and the flags are consumed first, so a variant that itself declares variants does not dispatch again — that is what keeps cross-linked pairs like ln ↔ exp from looping. A set flag with no matching variant signals user-error and still consumes the flags, so the next command starts clean.

14. Contextual digit entry

The digit keys (and _, ., #, @) start calc's normal number entry, but where the result lands depends on point at the first keypress and on the key that ends the entry (maf-digit-start in src/minibuffer.el). SPC pushes the number onto the stack exactly as in plain calc, wherever point is. RET is the contextual commit (maf-digit-commit-contextual): on a numeric leaf the entered number replaces it; on any other sub-formula it multiplies it, number on the left, with the product left literal so nothing distributes; on a relation node it multiplies both sides. The entry is an edit of the formula at point, and RET commits it, as it commits maf's text edits (maf-edit-commit).

Away from a sub-formula there is nothing to edit and RET pushes too — at home, in the line prefix, at EOL, in algebraic mode, for entries that escape to algebraic, and for interval entry (..). The entry minibuffer is calc's own (calc-digit-map), so the in-entry keys — _, :, @, #, .. — are unchanged but for the handful maf takes there, below.

C-<return> is SPC's keep-point sibling (maf-digit-commit-here): the same push, but point stays on the entry it was on instead of dropping to the home line, so the next command still resolves there. It has no RET counterpart, because RET keeps point already — the edit happens where point stands.

; is the fraction colon (maf-digit-colon), so 3 ; 4 enters 3:4 without a modifier. It is an alias, not an insertion — it re-dispatches calc's own calcDigit-key with the event spoofed to :, so calc's colon handling (the leading 1 for a bare ;, mixed numbers, format validation) applies unchanged. During a maf-edit session ; types : too (maf-edit-insert-colon); the literal semicolon — calc's row separator in matrix notation — moves to M-; there (maf-edit-insert-semicolon). While an incomplete object is on the stack — a vector, matrix, complex number, or interval being entered — the digit-entry ; steps aside for calc's own: it is the row separator of matrix entry, typed from inside digit entry, and a fraction there still goes in on :.

n and P commit the entry multiplied by pi (maf-digit-pi), so 2 n gives 2 pi and 1:3 n a third of it, symbolic either way. Being a value and its terminator in one key, n has no second key to split the two destinations across: the product goes where a value goes from this position — contextually on a sub-formula, as RET does, pushed anywhere else. e ends the entry and equates with the number typed (maf-digit-equal-to), the in-entry twin of e out in the stack: on x the entry 5 e gives x = 5. It is calc's own command-key termination, so the number becomes the command's argument and the push folds into the command's undo group; the cost is the e-notation the key was, which goes in through algebraic entry (' 1e6) instead.

j is a jump, not a value: the number names a stack level and point travels there (maf-digit-jump), landing at the entry's EOL — its margin — so the next command takes the whole entry. Level 0 is home; a level past the top of the stack lands on the top entry, as a jump past the end of a buffer lands on its last line. Nothing is entered or pushed, and the place point left is marked, so C-u C-SPC returns to it (home excepted, being one key away on maf-go-home). An entry that is not a whole number names no level and is refused, left standing in the minibuffer to be corrected. The key is calc's j selection prefix out in the stack, addressing a part of an entry where this one addresses a level; the cost is the command-key termination it was, so 3 j e no longer pushes the 3 and runs the prefix on it — push first (3 SPC) and the prefix is itself again.

n, P, e, and j step aside where the key is calc's own: inside a radix-prefixed entry — where a letter is a digit and which letters count depends on the radix (20#j is 19), and where a number is plainly a value, since no one writes a stack level in base 16 — and with maf-mode off in the calc buffer the entry belongs to. e, j, and RET stand aside for an incomplete object too: half a vector is no entry to equate with, jump from, or commit contextually, so inside one RET is calc's own terminator again, as it is with maf-mode off. SPC stays calc's own everywhere — the element separator inside an incomplete object ([ 1 SPC 2 ]), the plain push elsewhere. n and P work inside an incomplete object, so a vector can be filled with multiples of pi.

16. Modules

Major features that stand apart from the contextual-command core live as optional modules under modules/, toggled independently of maf-mode. A module is nothing but a global minor mode: it installs everything it needs when enabled and removes it all when disabled, and it works on its own, M-x-toggled like any minor mode, whether or not the module system is loaded. "Module" is just our name for one of these modes.

The registry in core/maf-module.el adds list-driven management on top. Loading a module file registers its mode under a short name with maf-register-module; maf-modules (a defcustom) lists the names that should be active. The list and the live modes stay in sync in both directions:

  • On activation, maf-modules-apply drives the modes from the list, enabling the listed modules and disabling the rest — run at load and whenever maf-modules is set through Customize.
  • When a mode is toggled directly, its hook writes the list back from live state (maf-module--reconcile), so maf-modules stays an accurate record of what is on. A dynamic flag suppresses this while maf-modules-apply runs, so applying the list never turns around and rewrites it.

The registry hooks into the modes, never the reverse: a mode body knows nothing of the registry, so each module guards its registration ((when (require 'maf-module nil t) ...)) and the feature stays fully usable with the registry absent — you just lose the list-driven management.

M-x maf-list-modules opens *maf-modules*, a dial buffer (pkg/dial) of every registered module as an on/off row, split into its own window. TAB or SPC flips the module on the current line in place: it calls the mode directly, so the reconcile above keeps maf-modules in step. Each module supplies its own description as the third argument to maf-register-module, echoed as point rests on its row, so the menu documents whatever is loaded without a central list to maintain. A description is written in two parts — one short sentence saying what the module does, a blank line, then three or four lines on what that means in practice. The menu heads the echoed text with the module's name, since help left standing in the echo area outlives the move off its row; Customize, which has room for one line, takes the summary alone.

Two module shapes have appeared, matching the feature's state:

  • Global mode. The history module (modules/maf-history.el) is one maf-use-history-mode global minor mode: enabling installs the recording hook and the calc-record advice and binds t d to maf-history in maf-mode-map; disabling removes them and cedes t d back to calc's calc-trail-display. Browsing is two side-by-side windows below calc: *maf-history* (maf-history-mode) on the left is the action log, one line per state, newest at the top, each prefixed by a git-style change marker (+ added, - removed, ~ changed in place, · for the oldest state, which has nothing to diff against), the current one marked; *maf-history-stack* (maf-history-stack-mode, whose map inherits the log's) on the right shows that state's whole stack. Moving in the log re-renders the stack beside it, so the session's course reads at a glance while stepping. Persistence (maf-persist-mode) is the same shape: enabling installs the save timer and the restore hook and binds l R to maf-saved-stacks (both it and the history's t d bring back an earlier stack, the history's from this session and l R's from any session) and l S to maf-save-stack, its on-demand companion; disabling removes them. The saved-stacks buffer is dial's, like the options menu — a row per save file, previewing its stack in a window beside the list as point moves (side by side, so a stack of any depth is read without scrolling), restoring one with RET, naming one with R — which on the session's own row names the running session, its lock moving with the file — and deleting one outright with D. The edit module too (modules/maf-edit.el): maf-use-edit-mode installs SPC / ` / C-o / ( in maf-mode-map when enabled and cedes them back when disabled — its body is just those bindings, the on-demand editing session (maf-edit-mode, turned on per gesture, not a feature switch) being separate.

    The render module (modules/maf-render.el) is the same global-mode shape with no background work of its own: maf-use-render-mode owns which command G runs, shadowing the Big-display peek rather than taking a key of its own (see A module's key over a default's below), and what the preview panel draws with (see One module's rendering, in another's panel). maf-render formats the whole entry at point with Calc's LaTeX language, runs maf-render-program once, and displays the returned SVG in an even split below Calc without selecting it. The program defaults to render-svg on exec-path, then ~/pkgs/ratex/render-svg; both the executable and RaTeX font size are customizable.

  • Globalized buffer-local mode. Highlighting is inherently per-buffer (an overlay per calc buffer), so modules/maf-hl.el keeps the buffer-local maf-hl-mode and wraps it in a define-globalized-minor-mode, maf-use-hl-mode, which turns the buffer-local mode on in every calc buffer. That globalized mode is the registered toggle; M-x maf-hl-mode still works standalone in a single buffer. The preview module (modules/maf-preview.el) is the same shape: maf-use-preview-mode turns the buffer-local maf-preview-mode on in every calc buffer, showing the entry at point — as it stands on the stack, unsimplified — in Big display in a floating panel at the top-right of the calc window. On a graphical frame the panel is a posframe child frame: parented to the calc frame and focus-refused, it stays out of the window manager's reach (no Alt-Tab, no focus). Where a child frame cannot be had — a text terminal, or no posframe — the same panel is drawn inside the window itself, one overlay per line it covers, each carrying a row of the panel and replacing the tail of a stack line long enough to reach it, so the panel occludes the stack rather than displacing it. Either way the panel is anchored to the top of the window, not to the text, so it stays in view regardless of how far the stack is scrolled — unlike a plain in-buffer overlay, which scrolls away once the stack outgrows the window. It hides itself while the whole buffer is already in Big display and during a maf-edit session.
  • A command of a module's, bound outside it. maf-preview-show (G, declared in src/bindings.el) puts up one panel over the entry at point — a peek, taken down again by the next command — and needs nothing of the module: no buffer-local mode, no globalized toggle. That is why its key is not declared through maf-bindings-module-keys like every other module key: a key that came and went with the toggle would take with it the way of working the toggle is turned off for — no panel underfoot, a look when wanted. The module toggle stays a plain on/off, and what it decides is only whether a panel follows point.
  • A module's key over a default's: a shadow. maf-render claims G through maf-bindings-module-keys, the key the peek above already holds. The compiler refuses two modules on one key — nothing there says which wins — but a module over a default it lets stand, because the toggle says it: the module's command holds the key while its mode is on and the default comes back when it goes off, so the key keeps its plain meaning for everyone who never turns the module on. It fits here because the two commands are one gesture: a single look at the entry at point, in a rendering the stack is not switched over to, and which rendering that look comes back in is the only thing maf-use-render-mode decides. A shadow covers the whole key and no more — a module may not turn a default's command key into a prefix, or bury a prefix family under a command, since neither is something a toggle could put back the way it found it.

  • One module's rendering, in another's panel. The same two commands meet again away from the keymap: the preview panel that follows point is typeset too while the render module is on. The panel asks rather than being told — maf-preview-render-function is a variable modules/maf-preview.el consults before falling back to Big, and modules/maf-render.el is what sets it — so neither module requires the other and the preview keeps working with the renderer absent. What comes back may carry a display property, an image included, so what a module can put in the panel is not limited to what Calc has a display language for. It is asked only where the panel can show that much: the child frame is a real buffer in a real frame, while the in-window panel is rows of text laid over stack lines, sized and clipped in columns, where an image has no width the arithmetic could use. A refusal — nil, or an error — is not a failure state but the Big rendering, so a formula LaTeX cannot write leaves the panel standing rather than taking it down.

    What the panel draws is one space whatever the formula, the rendering being in a display property rather than in the characters, so the check that leaves an unchanged panel alone compares text properties too (equal-including-properties). On characters alone every entry's panel reads as the same panel, and the first one previewed stays up however far point moves — the panel stops following, which is the whole of what it is.

    The panel asks once per command, which is the one thing here that renders without being asked to. RaTeX costs a few milliseconds, but a subprocess per keystroke is not worth spending on a formula that has not moved, so the module caches the last answer under the formula, the colour it was drawn in, and the size it was fitted to — the three inputs that can move it — and caches a failure under its key too, since a formula that will not typeset now will not typeset on the next keystroke either. The image is scaled to fit most of the frame: a rendering wide enough to leave the screen is a preview of nothing, and scaling it down whole beats clipping a formula off mid-term with no sign it was cut.

A module owns its whole lifecycle, including bindings: maf-mode no longer enables highlighting or the history, and bindings.el no longer holds the t d or in-place-editing keys.

The default maf-modules holds the features that belong in the base UX — maf-history, maf-hl, maf-edit, maf-render, and maf-formulas. The continuously-updating maf-preview remains available but is opt-in. The persist module (modules/maf-persist.el) is the exception: it writes save files to disk, so it stays out of the default and is opt-in — the dev instance adds maf-persist to maf-modules in project-init.el and calls maf-modules-apply, the documented Lisp way to enable a module.
