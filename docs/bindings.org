#+title: bindings module plan

* concepts
  - the `maf-bindings` module controls whether maf bindings are active at all
  - a *profile* selects the key layout: `calc`, `native` (default), `vim`
  - the bindings are what's native, not the commands: every profile runs
    mafcmds — the calc profile means calc's *layout*, maf's *commands*

* architecture: hub and spokes
  - one shared *base map*; each profile map is an independent sibling
    inheriting from base — no profile references another profile
  - base holds *command remaps only*, so it claims no keys and cannot
    collide with any profile's layout:
    #+begin_src elisp
      (define-key maf-bindings-base-map [remap calc-plus] #'mafcmd-add)
    #+end_src
  - remaps are audited (allowlist), not automatic: maf deliberately keeps
    some calc originals reachable as escape hatches (j E vs j e), and a
    remap would silently convert them. Excluding from the allowlist *is*
    the escape hatch — no wrapper commands
  - profile deltas are declared, and a declaration may target several
    profiles (source-level sharing, not inheritance):
    #+begin_src elisp
      (maf-bindings-define '(native vim) "x" #'mafcmd-expand)
      (maf-bindings-define '(vim) "w" #'maf-forward-noun)
    #+end_src
  - `maf-mode-map` stays the one registered map (stable dispatcher);
    switching = repointing its parent, live, nothing rebuilt:
    #+begin_src elisp
      (maf-bindings-set-profile 'calc)
    #+end_src

* lookup order (per profile)
  1. user bindings (per-profile user map first, then the common user map)
  2. enabled-module declarations
  3. profile defaults (minus compiled suppressions)
  4. base remaps
  5. calc's own map

* user configuration
  - user maps are never written or rebuilt by maf; they survive
    switches. Named maf-<profile>-user-map — `maf-calc-user-map`,
    `maf-native-user-map`, `maf-vim-user-map`, `maf-common-user-map` —
    and defprofile generates the name for a custom profile
    (maf-my-dvorak-user-map). Internal generated maps keep the long
    `maf-bindings-` names
    #+begin_src elisp
      (setq maf-bindings-profile 'vim)   ; before maf loads;
      ;; after load: M-x maf-bindings-set-profile, or customize
      (define-key maf-vim-user-map (kbd "g") #'maf-go-home)
      (define-key maf-common-user-map (kbd "<f6>") #'maf-timeline)
    #+end_src
  - principle: the user surface is plain elisp — real keymaps,
    `define-key`, `kbd` — for everything a keymap can express: adding,
    moving, overriding
  - the one exception is removal, which no keymap entry can say (nil
    exposes what lies below, `undefined` blocks calc too, and a sentinel
    command in the user map would shadow the fall-through it promises).
    So removal is the one API call:
    #+begin_src elisp
      (maf-bindings-unbind 'native ">")  ; > falls through to calc
    #+end_src
    suppressions live in the registry; the compiler omits the default
    from the generated map, so lookup falls through naturally, C-h k
    names calc's real command, and the call itself triggers the
    recompile. Scope: suppression removes *generated key declarations*
    — profile defaults and module declarations alike, for that profile;
    a suppressed prefix key (j) removes every generated descendant and
    exposes calc's whole prefix. Base remaps are not key declarations
    and still apply: suppression exposes calc's *layout*, but a calc
    command with a maf sibling still runs the sibling — suppressing +
    can never produce raw calc-plus
  - users can declare their own profiles — a profile is just a
    registered name plus two maps over base, nothing about the built-in
    three is special:
    #+begin_src elisp
      (maf-bindings-defprofile 'my-dvorak :clone 'native)
      (maf-bindings-define '(my-dvorak) "n" #'mafcmd-solve)
      (maf-bindings-set-profile 'my-dvorak)
    #+end_src
    tweaks to an existing profile don't need this — that's the user
    map's job; a profile earns its existence as a whole switchable
    layout
  - clone copies the source profile's *own defaults only*, at the
    declaration level; module keys are never copied — they follow the
    module's own targeting, live
  - ships after the built-ins work: custom profiles need the
    profile-aware displays, so both land together

* rules
  - dogfooding: the built-in profiles are declared through the same
    public API a user would use — `maf-bindings-defprofile` +
    `maf-bindings-define`, no privileged internal path. The built-ins
    are ordinary registry entries that happen to ship with maf, and
    double as the reference example for writing your own
  - modules declare their keys to the binding system; no raw define-key
    into `maf-mode-map` (a toggle must never erase a user override).
    Module targets are explicit profile names, `:all` deliberately —
    strictness governs modules too: under strict, the calc profile gets
    no module keys at all; under curated additions, only keys that
    displace nothing (options' ? shadows calc-help, so not there either
    way). Follows the strictness ruling below
  - registrations are owned and replaced as whole sets, so a reload is
    safe by construction: defprofile replaces that profile's default
    set, a module registration replaces that module's set, generated
    maps rebuild from the registry — a declaration deleted from source
    is gone after reload. User maps are never rebuilt
  - profiles govern the stack map and the digit-map overrides only;
    maf-edit, timeline, formulas, options keep their own fixed maps
  - digit-map changes are tracked installs: each declaration names the
    stock calc binding it expects to replace; install only when the
    current binding equals it (a user's direct customization is left
    untouched), save it, and uninstall restores it only if the current
    binding is still the one maf installed
  - key displays (module help, dial legends) derive keys from the active
    profile — no static key strings
  - the registry compiler validates at build time: a key cannot be both
    a command and a live prefix in one profile; module/profile and
    module/module key conflicts are errors, not precedence accidents

* calc profile
  - promise: zero surprises for a calc user; layout untouched
  - siblings run via base remaps on calc's own keys (+, a x, a S, ...)
  - keys whose calc command has no sibling stay calc's (x, h, scrolling)
  - no navigation bindings: silence means stock calc/emacs lookup

* vim profile
  - not vim's command model, just its navigation keys
  - hjkl / wb become motions; everything under stolen prefixes must be
    relocated or explicitly dropped (compiler-checked) — not yet: skeleton
    keeps today's bindings
  - design the relocation table before implementing; this profile lands
    last

* open decisions
  - [ ] calc profile strictness: strict (only sibling remaps — matches
    the written promise; recommended) vs curated additions on unbound
    keys
  - [ ] bindings module off: truly zero maf keys (M-x is the way back;
    recommended) vs a bootstrap key for the module menu
  - [ ] vim motion semantics: h/l by char or noun? j/k by line or entry?
    w/b = noun motion?
  - [ ] vim relocation table for the h/j/k/l/w/b families
  - [ ] digit-entry customization surface: per-profile digit declarations
    for users, or a documented API?
  - [ ] custom profiles and module keys: with explicit module targets, a
    custom profile is in no module's list — inherit the clone source's
    module targeting (provenance), or require the profile author to
    declare?
  resolved: module-vs-profile precedence (conflicts are compiler errors,
  so precedence rarely decides anything); profile persistence (customize
  only — maf-persist is a separate concern); user profile seeding for
  the profile's own defaults (declaration-level clone)

* phases — skeleton first
  Build the architecture now; decide no new binding content. Today's
  bindings are carried through the registry declared for *all three
  profiles*, so every profile behaves identically — switching works but
  changes nothing — until the content phases differentiate them.
  - [ ] 1. snapshot current behavior in step tests: effective bindings,
    remaps, prefix descendants, module on/off, digit-entry, real
    key-binding answers in a calc buffer
  - [ ] 2. registry + compiler: base + three profile maps + user maps +
    compiled suppressions; every profile reproduces today's map exactly
    (behavior, not bytes); conflict validation
  - [ ] 3. one atomic landing: module + digit-map declaration conversion
    (tracked installs), then dispatcher, profile defcustom + switch
    command, live switching, and profile-aware key displays. Not split:
    raw module define-keys under the dispatcher would outrank user maps
    and falsify the lookup order, and a user's first rebind in a user
    map falsifies static key displays
  - [ ] 4. document user configuration and migration from direct
    maf-mode-map bindings

* later: profile content (out of scope for the skeleton)
  - [ ] audit the remap allowlist and fill the calc profile
  - [ ] classify today's native-profile bindings: remap-covered vs
    displacement delta
  - [ ] user-defined profiles (displays land earlier, with the switcher)
  - [ ] vim: motion semantics, relocation table, then the profile
